# H800 small-M, indexed GEMV and MoE preparation

The extended Q4 comparison passes numerical validation in **108/108**
shape/workload/cache cells. **105/108** confirmed cells are within 5% of
both FP32-accumulating controls. Three small dense cells remain open.
This is CUDA/H800 evidence, not PPU or llama.cpp model admission.

## GEMV scope

- Dense M=1 through 7: one shared weight matrix, independent activation
  rows, one multi-row launch. No host loop around M separate GEMVs.
- Indexed M=1: 256 resident experts, eight nonadjacent GPU expert IDs;
  both one shared activation and eight independent activation vectors.
- Six N/K families, warm and rotating. Rotating touches at least 2.25×
  the queried 50 MiB H800 L2 capacity in distinct selected weight bytes.
- FP16 A, FP32 accumulator/reduction/output, S1 with no inter-CTA reducer.
  Padded input/output strides, guards, zero-A checks, deliberately wrong
  expert IDs, and changing A/IDs on the same captured graph are tested.
- Official GGUF FP64 dot oracle; original nonzero GGUF weights and new
  random FP16 activations. Expert matrices are distinct N permutations of
  that source matrix, not independently randomized GGUF tensors.
- Xplane and supplied raw reference preserve per-weight FP16 dequantization;
  affine K-pack arms apply scale/min in FP32 after the group dot. All three
  accumulate in FP32, but this is not a layout-only arithmetic comparison.
- Six interleaved confirmation rounds × 15 event samples; first graph
  launches excluded. Timing excludes packing, routing and llama adapters.

Open cells: M2/N512/K2048 rotating (+7.15% vs reference),
M4/N512/K2048 warm (+7.96% vs Xplane), M2/N1024/K5120 warm
(+8.24% vs Xplane). The last cell's two/four-column affine alternatives
also failed to improve its screen result; do not substitute them as fixes.

The frozen selection is an experiment inventory, not a proposed 108-rule
production heuristic. It preserves the tested body and bounded recipe
shortlist per cell. Expanding configurations and separating dense indexing
from device-ID indexing fixed most initial small-M gaps. Several shared-B
multi-row and scalar-reader alternatives were numerically correct but slow;
they remain experimental, not default code paths.

## MoE prepare

The experiment reuses production router/descriptor definitions and the
shipping independent oracle. It compares original preparation with:

1. M1 pairwise FP16 stores for gathered A, preserving scalar unaligned
   heads/tails and odd-K fallback.
2. M2–4 warp-local top-8 selection and one directory-prefix computation
   reused across gate/up/down when all TileM values cover the per-expert
   row count. Projection-specific shapes/pointers still remain separate.

No B weights are moved. The work is activation gather/conversion, routing,
row IDs, offsets, pointer arrays and launch directories. A one-CTA version
that computes routing only once was also tested: limiting gather parallelism
made it slower (approximately 24–26 us for the larger cases). Removing
duplicate arithmetic alone is not enough.

96 contexts cover K=512/2048/3072, tokens=1/2/3/4, merged/separate gate-up,
and four router modes. Each context passes seven changed-input graph
replays; the modified router also passes 4,096 raw-bit ID/weight fixtures.
Four A/B timing rounds use model-like gate/up/down splits S2/S2/S1,
15 samples each. Original fallback cases and odd-K behavior pass as well.

cover M5–7. The preparation oracle substitutes completed projection
fixtures for PPU GEMMs; it is not a fused model benchmark.
