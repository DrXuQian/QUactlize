# dense vs grouped(L=1): where a performance difference can come from

The acceptance criterion is `time(dense) <= time(grouped, L=1)` at the same shape, checked by
`analyse.py --invariant`. This is the source-level companion: what the two paths actually do differently, so a
measured gap can be **attributed** rather than guessed at, and so a violation points somewhere specific.

Written 2026-08-05, before the 060/063 fix lands. The one line the fix changes is marked.

## Why the inequality should hold by construction

Grouped with one expert computes the same GEMM through the same mixed-input collective. Every structural
difference is grouped doing **more** work:

| | grouped, L=1 | dense | who pays |
|---|---|---|---|
| kernel schedule | per-`gs` fine-grained ladder (`moe_grouped_ppu.cuh:447`) | **one hardcoded `KernelTmaWarpSpecializedCooperativeMixedInput`** (`test_lowbit_dense_bench.cu:181`) | ← **the fix changes this line** |
| epilogue | `EpiloguePtrArraySimtVectorized` — indexes `ptr_D[l]` | `EpilogueSimtVectorized` — direct `D` + stride | **grouped**: one indirection per output tile |
| output pointers | host-built `ptr_A/ptr_B/ptr_D[L]` + `stride_D[L]` arrays | plain pointers | **grouped**: setup + device reads |
| scheduler | GroupScheduler; m-tile prefix decode, `group_M[]`, `group_row_offsets` | plain `blockIdx` | **grouped**: per-CTA decode |
| workspace | m-tile prefix written into it | not needed for this | **grouped** |
| mainloop | the same collective | the same collective | — |
| timing loop | 3 warm-ups then `iters × fn()`, events outside | `iterations × gemm.run()`, `initialize` outside the loop | neither |

At L=1 the grouped extras are small but they are all one-signed. **So `dense <= grouped(L=1)` is not a hope; it
is what the structure predicts.** A violation is therefore informative rather than noise.

## If dense measures SLOWER, these are the candidates

In the order I would check them, because the first two are not kernel problems at all and would be misread as
such.

### 1. A config the dense side cannot reach — a SEARCH-SPACE gap, not a kernel gap

The two benches do not search the same set:

* `test_lowbit_dense_bench` compiles `benchmarks/lowbit_dense_configs.inc` — 227 rows generated by
  `emit_tactic_configs` for `(bits=4, tile_k=64)` under the pruning policy.
* `test_scalefirst_bench` carries a **hand-written** list per width, and the record says its `w64x32` rows are
  worth **+8.6 points for int4** and were missing from an earlier grid entirely.

If the grouped winner's geometry is absent from the dense table, dense loses the comparison while running an
identical kernel. **Check this first**: compare the winning config strings, not just the times. Both tables do
contain `w64x32` today (29 rows in the dense `.inc`, at tiles `64x128` and `128x64`), but they are different
sets and only overlap by construction, not by design.

### 2. A different TileK

`scale_first` TileK is `256/bits`, so int4 is 64 on both, and the dense bench's default matches. But a `TSK=`
override, or the fix routing dense through a schedule with a different `ScaleTileShape`, changes the arrangement
and the comparison at once. **A dense run and a grouped run at different TileK are not comparable at all** — TileK
is the axis that also changes the offline layout.

### 3. Something dense does that grouped does not

The table above has no such row today, which is the point: after the schedule selection is shared, the dense path
should be a strict subset of the grouped path's work. If a difference appears here later, it is new.

### 4. The epilogue, in the direction that would surprise

`EpilogueSimtVectorized` (dense) should beat `EpiloguePtrArraySimtVectorized` (grouped). If it does not, the
pointer-array epilogue is doing something the direct one is not — worth an `acu` capture rather than a guess.

## What the 060/063 fix changes, and what it does not

It changes **one thing**: how the schedule is selected. `ppu_group_schedule.hpp` becomes the single definition of
the `gs -> KernelAiuMultistageMixedInputFinegrainedGs{16,32,64,128}` ladder, consumed by dense, grouped and the
shipping backend, with a `static_assert` so an unsupported group size fails while building rather than as a
device assert that surfaces three frames later as "Failed to query occupancy".

It does **not** change the epilogue, the scheduler, the pointer arrays or the mainloop. So the table above is
still the complete list of asymmetries afterwards, and the invariant's prediction is unchanged.

## The baseline is grouped, not dense

`test_lowbit_dense_bench` **has never produced a validated number**: it asserts on its first config at gs=32 and
every recorded figure in `docs/BACKTEST.md` section A came from `test_scalefirst_bench` (grouped) or the
grouped L=1 path. So after the fix:

* "the dense bench runs" is not evidence that it is right;
* the check is `dense(fixed) ≈ test_scalefirst_bench at the same shape and gs`, and the recorded targets are
  that bench's, not the dense bench's;
* `analyse.py --invariant` then states the inequality over the two sample files.

A dense path that runs and disagrees with the grouped numbers is a worse outcome than one that asserts, because
the assert is loud.
